# 业务发现应用的边界与 GroundGraph 收敛建议

日期：2026-09-30  
审查基线：`067103529e9593326bf13e4b082dddb9d179d4e7`  
状态：源码审查与实施建议；不是已完成的重构，也不是运行验收报告。

## 结论

建议将跨代码库的业务发现、行业差异分析、人工审定与目标系统草稿导出放在独立应用层。GroundGraph 提供可替换的代码事实、索引和证据查询。先复用现有证据/候选模型，不立刻复制图存储或建设另一套本体平台。

独立应用不等于重新编写解析器。适配边界要允许直接源码扫描、GroundGraph 索引等后端接受同一组验收样本，输出同一证据契约；以实测收益决定复用范围。

## 源码发现

### 1. 聚类是候选分组，不是业务边界判定

位置：`crates/groundgraph-engine/src/feature_cluster.rs` 模块注释与 `detect_communities_with_resolution`；`business_pack.rs` 模块说明。

当前使用调用/导入图的 Louvain 社区划分整理业务证据。该算法适合导航和上下文分组，但高耦合不证明同属一个业务域：公共基础设施可能连接多个域，事件驱动又可能让真实业务依赖缺少静态调用边。

建议保留算法，降低输出解释的强度。聚类不得直接决定插件边界、对象归属、生命周期或业务等价。应用层应支持人工拆分/合并、证据反驳与多种候选分组并存。

### 2. 两套 propose 的用途不同，不能因名字相似直接删除

位置：`connect.rs::propose_evidence` 与 `business_pack.rs::propose_business_pack`。

- `connect propose` 整理需求、文档、实现和测试的关联证据
- `propose` 整理候选模块的业务证据

建议在专用应用中不暴露两套含糊入口，而以“需求追踪”和“业务发现”区分。可共用证据加载、分页、出处和导出基础设施；需要兼容期后再考虑命令迁移，不能认定两者完全重复。

### 3. connect apply 的接受结果不能代表业务确认

位置：`connect.rs::apply_candidates`、`validate_candidate`、`CandidatesDocument`。

源码中可见：
- 验证器检查 docs/implementations/tests 引用的可解析性及至少有一项引用
- 候选的 requirement 字符串被直接用作 manifest 键；该验证路径未检查目标需求节点是否存在
- 文档的 schema_version 被反序列化，但 apply 路径未据此拒绝不支持的版本
- 写入的 manifest 不保留候选的 confidence/rationale，也没有逐项业务审定记录

这不是完整运行复现；结论限定于上述代码路径。调用命令可以表示操作者选择导入，但不能把“引用能定位”自动解释为“业务语义已由人确认”。

后续单独修复建议：
1. 未知需求与不支持的候选版本在写入前拒绝
2. 增加反例测试：真实符号 + 不存在的需求，未来版本 + 有效引用
3. 专用应用区分可解析、待审、人工确认、已导出；保留来源和审定记录

### 4. 配置归一化值得收敛，但先补作用域测试

位置：`config.rs::EngineConfig::normalized`。

既有 `languages` 是规范入口，但内部仍映射到旧语言配置。进入通用 tree-sitter 路径时，各语言的 paths/exclude 被合并到公共列表，逐语言作用域的区别在这个中间表示中丢失。未知语言 ID 则直接跳过。

这提示两个应优先验证的风险：
- 一种语言的排除规则是否影响另一种语言
- 拼错语言 ID 是否导致没有按预期扫描而仍被视为成功

建议先增加混合语言、不同根目录、不同排除规则的集成反例，再改成逐语言执行计划。旧配置通过显式迁移/弃用提示收敛，不能直接删除后让旧项目失效。

### 5. graph-equiv 已有必要的限制声明，应保留

位置：`graph_equiv.rs` 模块说明与报告字段。

当前明确说明节点/边计数和名称覆盖不证明图同构或行为等价；报告包含 behavioral_equivalence 状态。该能力可用于发现差异和安排核对，不能充当业务迁移验收。

建议在专用界面显示为“结构差异/覆盖”，并把行为回放、数据约束和规则对照列为独立证据。不要删除已经存在的限定说明。

## 保留、可选、收敛与移出

| 类别 | 建议 |
| --- | --- |
| 保留 | 稳定代码身份、解析与绑定、带出处的关系、未解析诊断、快照信息、候选/确认区分 |
| 可选 | 通用图可视化、社区聚类、未进入当前样本的语言后端和分析命令；按需启用，不按当前单一项目需求删除通用能力 |
| 收敛 | 旧配置入口、重复证据加载、含糊的命令文案；先兼容迁移与反例测试 |
| 独立应用负责 | 跨项目术语对齐、行业/客户差异、业务对象和规则候选、反例、人工审定、目标插件草稿导出 |
| 不可据现有证据删除 | 历史迁移、兼容性入口、看起来“没调用”但可通过 CLI/MCP 使用的功能 |

现有审查不足以证明某个完整模块无人使用；不按文件数量或本次未使用直接删除。

## 最小实验

先限定一个采购到货链路，人工建立带出处的答案集，再比较：
A. 直接读取源码/配置的专用提取器；
B. 使用 GroundGraph 索引与证据查询的专用提取器。

两条路径固定相同源码提交、范围、答案集和人工审定标准。第一阶段无需真实业务数据或外部模型调用。若后续使用模型，应固定模型/提示词/预算并遵守客户数据边界。

答案集至少包含：
- 静态直接调用、编号分派、重复编号、动态编号
- Java 接口实现注册、流程配置与处理器绑定
- SQL/实体数据依赖、规则判断和事件关联
- 故意缺失源码、配置不完整、无法解析、扫描截断
- 相同模板复制的项目不能计为独立行业证据

输出逐条记录仓库快照、路径/行号或语法位置、证据类型、提取器版本、候选状态、未解析原因。目标模型不必拥有第二套图数据库；先从现有记录投影，并独立保存必要的人工审定信息。

评估：
- 人工标注范围内的候选精确率和召回率，按对象/动作/规则/依赖分别报告
- 出处可定位率与快照一致性
- 动态/缺失/歧义是否被正确标为未知，而非算作已完成
- 冷启动、增量变更耗时、峰值资源、人工修订耗时
- 删除/改名/移动代码后，旧候选和审定结果能否正确失效

只有当 B 在质量或成本上有明确收益时，才继续扩大依赖。若仅少量解析能力有收益，可保留适配层并替换其余实现。
